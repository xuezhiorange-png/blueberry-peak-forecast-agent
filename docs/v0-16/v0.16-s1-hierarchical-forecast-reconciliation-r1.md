## Hierarchy and privacy

Only BASE → REGION → COMPANY is admitted. FARM and FACTORY are not hierarchy
nodes. Region IDs and labels are the exact registry `region_scope` strings; they
are not coordinate-derived geography. In particular, a registry review-status
scope is not upgraded to a certified geographical region by aggregation.
Missing, blank or non-string scope on an active Base fails closed.

Active semantics match Operational Peak exactly: `bool(entry.get("active", True))`.
Inactive entries remain in the audit snapshot but never enter expected children.
Snapshot ordering is regions by exact ID, bases by ID, child IDs sorted.

Company ID is `COMPANY_AGGREGATE_ROOT_V1`, label `ALL_REGISTERED_BASES`, semantics
`TECHNICAL_FORECAST_AGGREGATION_ROOT_NOT_LEGAL_ENTITY_IDENTITY`. No legal company
master data is invented.

Authenticated read/discovery returns a sanitized snapshot: technical root,
region labels, Base IDs/names, active flags and hashes. It contains no productive
areas, coordinates, raw registry document, private paths, environment values or
credentials. The same sanitized canonical snapshot is persisted for old-run reads.

## Reconciliation contract

`V0_16_HIERARCHY_R1` / `HIERARCHICAL_BOTTOM_UP_EXACT_SUM_R1` performs bottom-up
exact Decimal sums only. No clipping, rescaling, imputation, fallback, fuzzy
identity, model override, manual hierarchy override or parent-model fitting.
Source IDs must be nonempty, unique positive integers; canonical order is sorted.
Rerun lineage is intentionally not added in R1: changed inputs create a new
execution identity; identical inputs reuse the existing run.

Each source is reloaded using `OperationalPeakRunRepository.get()`. Source
authority must equal the hierarchy's pinned Operational Peak authority. Policy,
baseline, season, origin, business boundaries, weather flag and complete daily
calendar must match. Unknown/inactive/outside-target or duplicate Base sources
are rejected. No implicit selection of the newest source run.

COMPLETE requires the exact expected active Base set. Company direct Base sums
and Base→Region→Company sums are computed independently and checked for exact
equality. Region breakdown and its digest are retained and verified on reload.
H7/H15 use existing `summarize_window`; single-day and rolling-7 peaks are
recomputed from the aggregate curve, earliest-date/start tie wins. Child peaks
are never summed. Short horizons are not padded. Season total is null with
`NOT_APPLICABLE_SOURCE_HORIZON`.

Missing children produce a persisted `INCOMPLETE_CHILD_COVERAGE` attempt, not a
failed run: official aggregate/totals, H7/H15 and peaks are null, daily rows are
empty, and missing IDs/counts/hashes are explicit. No diagnostic subtotal is
returned in R1, avoiding ambiguity with official output. Missing child ≠ zero.

Execution identity binds schema, target, hierarchy hash, sorted source IDs,
source execution/result hashes, compatibility key and policy. Result identity
also binds status, coverage, output curves/windows/peaks, parity and limitations.
No filesystem path or timestamp participates in deterministic execution identity.

## Persistence, concurrency and recovery

Migration creates `hierarchical_forecast_run`, `hierarchical_forecast_daily`, and
`hierarchical_forecast_source`. Sources have FKs to saved Operational Peak runs;
there is no source back-reference update. Counts/status, daily index/date and
source Base/run uniqueness are enforced in both application and database.
SQLite/PostgreSQL triggers reject UPDATE and DELETE on all three new tables.
Insert guards bind daily calendar/count and source refs/count to the parent.
Populated downgrade refuses with `HIERARCHICAL_FORECAST_DATA_PREVENTS_DOWNGRADE`;
empty downgrade/upgrade is supported.

Create uses the caller-owned transaction with a nested savepoint; flush and
canonical reload occur inside the savepoint. Failed reload rolls back the whole
attempt. The unique execution key plus savepoint conflict recovery handles two
concurrent READ COMMITTED creates without sleeps or leaked IntegrityError.

GET does not read current authority or forecast again. It rebuilds from stored
snapshot, parent, daily and source refs, canonically reloads referenced immutable
source runs, recomputes coverage/arithmetic/windows/peaks/parity and all identities,
then compares every persisted result field. Parent, child, source or snapshot
corruption fails closed. Existing source forecasts are never modified.

## Interfaces

- POST/GET `/api/v1/hierarchical-forecast-runs`
- GET `/api/v1/hierarchical-forecast-runs/{run_id}`
- GET `/api/v1/hierarchical-forecast-runs/{run_id}/daily`

History filters target type/ID, season, origin and reconciliation policy, with
created_at DESC / id DESC keyset pagination, default 20, maximum 100. Each history
item is integrity-verified; summary responses do not contain daily payloads.

CLI: `python -m backend.app.cli hierarchical-forecast-run create --input request.json`;
`get --run-id ID`, `list`, `daily --run-id ID`. Every command supports
`--output -` or file output; create accepts `--input -` for stdin.
The root CLI file is hash-bound by V0.11's historical public manifest and remains
byte-identical. S1 is registered through its existing Operational Peak CLI hook,
which only delegates the new resource to the S1 thin adapter; existing source CLI
commands and business behavior remain unchanged. No historical manifest is rewritten.

MCP thin tools: `create_blueberry_hierarchical_forecast_run`,
`get_blueberry_hierarchical_forecast_run`,
`list_blueberry_hierarchical_forecast_runs`,
`get_blueberry_hierarchical_forecast_daily`. Existing ten tool schemas and their
frozen hashes remain unchanged; four new tools are appended before optional
research tools. Code only: no connector registration, production deployment,
configuration change or new port. `MCP_DEPLOYED=false`.

Errors use stable value-free codes, including authority/source/target violations,
not-found, persistence-integrity/conflict and write-failure. HTTP/MCP/CLI never
return exception text, SQL, connection URLs, paths or stack traces.
