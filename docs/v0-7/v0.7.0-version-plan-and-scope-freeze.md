This document freezes the V0.7 research and validation contract. It does not
train a model, generate a dataset, calculate weather features, modify runtime
code, add a migration, or authorize any V0.7 Slice.

## 1. Single business objective

V0.7 answers two separate questions:

1. How well does the current area-plus-history model perform under strict
   independent multi-season out-of-time validation?
2. Under the same folds, Bases, rows, business-season boundary, and metrics,
   does adding leakage-safe weather information provide reproducible
   incremental value?

The version must not turn exploratory backtests, fixtures, green CI, or the
ability to serialize a model into a production accuracy claim.

## 2. Historical data boundary

The formal historical scope is the three already-authorized historical harvest
seasons:

```ini
SEASON_1=2023-2024
SEASON_2=2024-2025
SEASON_3=2025-2026
THREE_SEASON_HISTORICAL_HARVEST_AVAILABLE=true
THREE_SEASON_INDEPENDENT_MODEL_ACCEPTANCE_COMPLETE=false
```

V0.7 reuses the existing historical-harvest authority, Base identity mapping,
area authority, business-season boundary, and coverage semantics. It must not
create a second historical-fact framework. The following distinctions remain
mandatory:

- confirmed zero is not missing data;
- unresolved identity is not a valid mapped label;
- partial coverage and unknown dates remain explicit;
- business-season boundaries and right truncation remain explicit;
- missing days are never silently filled with zero, interpolation, or a model
  estimate.

The existence of three seasons is a data-availability fact. It does not imply
that every Base-season is complete, that every identity is resolved, or that a
formal three-season independent model acceptance has already passed.

## 3. Frozen Model A

Model A is the existing V0.5 frozen baseline:

```ini
MODEL_A=AREA_PLUS_HISTORICAL_HARVEST
TOTAL_MODEL=BASE_AWARE_BASELINE_R1
TEMPORAL_MODEL=AREA_DAILY_RIDGE_V1_FROZEN_REFERENCE
ALGORITHM_CHANGED=false
HYPERPARAMETER_SEARCH=false
VALIDATION_SEASON_USED_FOR_TUNING=false
```

Rolling refit on past data is allowed only in the strict meaning that Fold B
may fit the same frozen algorithm using 2023–2024 and 2024–2025 before scoring
2025–2026. The validation result cannot be inspected and used to change the
algorithm, features, objective, or parameters before rescoring.

## 4. Rolling out-of-time folds

Random splitting is prohibited. The only primary historical folds are:

| Fold | Training seasons | Validation season | Role |
| --- | --- | --- | --- |
| A | 2023–2024 | 2024–2025 | forward diagnostic |
| B | 2023–2024 + 2024–2025 | 2025–2026 | later forward validation |

```ini
VALIDATION_METHOD=ROLLING_OUT_OF_TIME
RANDOM_SPLIT_ALLOWED=false
FUTURE_TO_PAST_LEAKAGE_ALLOWED=false
THREE_SEASONS_ARE_NOT_THREE_SYMMETRIC_LEAVE_ONE_SEASON_OUT_FOLDS=true
```

The two origins must retain their actual coverage, matched Base, partial-season,
unknown-date, and right-censoring status. A three-season source does not create
three symmetric validation folds because a future season must not train a
prediction of a past season.

## 5. Frozen evaluation contract

Model A and Model B use the same formal metric policy and report all results at
the following levels:

```text
GLOBAL
PER_BASE
PER_SEASON
MATCHED_HISTORICAL_BASES
COVERAGE_LIMITED_BASES
```

### Season total

- MAE;
- pooled WAPE (`sum absolute error / sum absolute actual`);
- Bias;
- relative error.

### Daily curve

- daily MAE;
- pooled daily WAPE;
- daily Bias.

### Single-day peak

- peak quantity error;
- peak quantity WAPE;
- signed peak-date error in calendar days;
- absolute peak-date error in calendar days.

### Rolling seven-day peak

- seven-day cumulative quantity error;
- seven-day cumulative WAPE;
- signed seven-day start-date error;
- absolute seven-day start-date error.

Every result also reports:

```text
train Base count
validation Base count
matched Base count
daily comparable row count
complete Base-season count
partial Base-season count
missing/unknown day count
```

Existing S3 metric definitions are reused. A missing day remains not
comparable, while a formally confirmed zero remains a valid actual. Undefined
zero-denominator metrics are explicit `NOT_COMPUTABLE`/`UNDEFINED` states and
are never reported as zero error.

```ini
BUSINESS_ACCURACY_THRESHOLD_STATUS=NOT_FROZEN
PRODUCTION_ACCURACY_APPROVED=false
```

No numerical business threshold is invented in V0.7 planning.

## 6. Weather information boundary

V0.7 separates three weather meanings:

### A. Past observed weather

Weather that had already occurred before the forecast origin may be used when
it was actually visible at that origin:

```ini
PAST_OBSERVED_WEATHER_AS_INPUT=ALLOWED
```

### B. As-issued forecast-time weather

Archived forecast snapshots may be used only when the snapshot was genuinely
available at the origin:

```text
weather.issued_at <= prediction_origin
weather.known_at <= prediction_origin
```

The snapshot must retain provider/run identity, issue/fetch/valid times,
horizon, raw/normalized hashes, Base binding, and missing fields. An absent
archive cannot be reconstructed after the fact.

```ini
FORECAST_TIME_WEATHER_AS_INPUT=ALLOWED_ONLY_WITH_ARCHIVED_AS_ISSUED_SNAPSHOT
```

### C. Future realized weather

Weather that occurred after the origin, including realized/reanalysis data used
as a substitute for a forecast, is forbidden as a production-like input:

```ini
FUTURE_REALIZED_WEATHER_AS_PRODUCTION_INPUT=FORBIDDEN
ORACLE_DIAGNOSTIC_ALLOWED=true
ORACLE_RESULT_PRODUCTION_ELIGIBLE=false
```

Oracle/upper-bound diagnostics must be labeled research-only and must never be
presented as deployable forecast evidence.

## 7. V0.7-S1 — Formal multi-season baseline validation

```ini
V0_7_S1=FORMAL_MULTI_SEASON_BASELINE_VALIDATION
V0_7_S1_IMPLEMENTATION_AUTHORIZED=false
```

S1 first validates Model A under Fold A and Fold B. It must produce:

- Fold A metrics;
- Fold B metrics;
- combined out-of-time metrics;
- per-Base metrics;
- per-season metrics;
- error distribution and peak error analysis;
- coverage report;
- frozen dataset and split manifests;
- deterministic prediction/result hashes.

S1 acceptance requires:

```ini
THREE_SEASON_DATA_AUTHORITY_PASS=PASS
ROLLING_OOT_FOLD_A_PASS=PASS
ROLLING_OOT_FOLD_B_PASS=PASS
VALIDATION_LEAKAGE_PASS=PASS

ROLLING_7DAY_METRICS_PASS=PASS
PER_BASE_REPORTING_PASS=PASS

```

S1 must report measured error, not a binary accuracy approval:

```ini

```

## 8. V0.7-S2 — Weather dataset and leakage-safe feature freeze

```ini
V0_7_S2=WEATHER_DATASET_AND_LEAKAGE_SAFE_FEATURE_FREEZE
V0_7_S2_IMPLEMENTATION_AUTHORIZED=false
```

S2 creates no provider or model promotion. It audits the existing authorized
weather sources and establishes a small, reproducible weather dataset contract
for later comparison. Candidate fields are temperature, precipitation, solar
radiation, wind, and humidity only where authoritative and available.

The initial policy envelope may consider recent and cumulative windows such as
7-day, 14-day, 30-day, and season-to-date. The exact feature list is frozen by
S2 only after source availability and point-in-time visibility are audited; no
feature search is authorized by this plan.

GDD is not added by assumption:

```ini
GDD_STATUS=NOT_IN_MODEL_UNTIL_DEFINITION_FROZEN
```

If no already-frozen base temperature, daily min/max policy, and horizon
aggregation definition exists, GDD remains outside the formal candidate set.

S2 acceptance requires:

```ini
WEATHER_SOURCE_AUTHORITY_PASS=PASS
WEATHER_TIME_VISIBILITY_PASS=PASS
FEATURE_LEAKAGE_GATE_PASS=PASS
REALIZED_FUTURE_WEATHER_REJECTED_AS_PRODUCTION_INPUT=PASS
WEATHER_FEATURE_POLICY_FROZEN=true
```

## 10. V0.7-S4 — Model comparison and version conclusion

```ini
V0_7_S4=MODEL_A_B_COMPARISON_AND_VERSION_CONCLUSION
V0_7_S4_IMPLEMENTATION_AUTHORIZED=false
```

S4 produces the full Model A and Model B reports, Fold A/B comparisons,
combined comparison, per-Base and per-season comparison, error/coverage
limitations, weather conclusion, and next recommendation.

For every main metric it reports:

```text
Model A metric
Model B metric
absolute delta
relative delta
Fold A delta
Fold B delta
direction consistency
```

It also reports per-Base improved, degraded, and unchanged counts, and checks
whether any apparent overall improvement is driven by one or two large Bases.
Weather conclusions are restricted to this vocabulary:

```ini
WEATHER_INCREMENTAL_VALUE=SUPPORTED_BY_HISTORICAL_OOT_EVIDENCE
WEATHER_INCREMENTAL_VALUE=NOT_DEMONSTRATED
WEATHER_INCREMENTAL_VALUE=UNSTABLE_ACROSS_SEASONS
WEATHER_INCREMENTAL_VALUE=INCONCLUSIVE
```

`SUPPORTED_BY_HISTORICAL_OOT_EVIDENCE` is still not prospective production
validation. V0.8 or production promotion is never automatic:

```ini
V0_8_OR_PRODUCTION_PROMOTION_AUTHORIZED=false
```

## 12. Explicit non-scope

The following are outside V0.7:

- real-time production deployment;
- automatic model retraining or automatic model selection;
- broad hyperparameter or feature search;
- multi-crop or multi-organization support;
- multi-factory routing, peak shaving, or factory optimization;
- UI refactor or MCP expansion;
- weather production-model promotion;
- V0.8 implementation.

V0.6 PIT shadow evidence may continue to accumulate naturally, but it is not a
reason to implement V0.7 outside this frozen Slice order. V0.7 itself does not
modify V0.6 snapshots or retrospectively manufacture forecast archives.

## 15. Final scope statement

V0.7 is a controlled multi-season validation and weather-aware experiment
version. Its primary scientific requirement is a fair, held-out comparison of
the frozen historical Model A against a minimally changed, leakage-safe Model B.
It does not assume that weather will win, and it cannot promote a model merely
because an aggregate metric improves in one Fold or one Base.
