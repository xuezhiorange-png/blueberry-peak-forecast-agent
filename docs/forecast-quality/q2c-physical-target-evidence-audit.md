## 1. Audit boundary

This audit covers the checked-in repository at the authorized base: application
schemas, services, ORM models, migrations, tests and forecast-quality
documents. No live PostgreSQL business rows were queried and no external farm
ERP, picking, weighing, spreadsheet or factory system was accessed.

```text
SOURCE_DISCOVERY_SCOPE=CURRENT_REPOSITORY_AND_CHECKED_LOCAL_ARTIFACTS_ONLY
LIVE_DATABASE_SOURCE_DISCOVERY_STATUS=NOT_EXECUTED
EXTERNAL_BUSINESS_SOURCE_DISCOVERY_STATUS=NOT_AUTHORIZED_NOT_EXECUTED
REAL_BUSINESS_DATA_STATUS=NOT_VERIFIED
```

The conclusions below are therefore about repository contracts and production
paths, not proof that a real external source has no data.

The Q2A/I5 source path is present on the audited main commit. The relevant
contract and code surfaces are:

| import unit | same enum/model surfaces | closed value includes `KG` |

The repository path establishes a canonical actual-label contract. It does not
provide the business attestation needed to prove that a particular external
source or forecast candidate measures the identical physical boundary.

## 3. Forecast-side evidence

### 3.1 Core Forecast and Task 9

The V0.1 core forecast contract and
`backend/app/core_forecast/{schemas.py,service.py,persistence.py}` identify:

```text
TASK9_HARVESTED_BASIS=MARKETABLE
FORECAST_TARGET_CANDIDATE=model_harvested_marketable_quantity_kg
```

The candidate is generated by the model/state pipeline. The repository does
not prove that this model output is an observed scale weight at the instant of
FARM_PICK, nor that it includes the same rejection, sorting and post-harvest
boundaries as the actual label.

The V0.1 physical curve also computes:

```text
effective_marketable_quantity_kg
  = model_harvested_marketable_quantity_kg
  * sorting_retention_rate
  * postharvest_retention_rate
```

This is evidence of a later retained quantity boundary. It is not evidence of
FARM_PICK equivalence. The retention policy source, version and hash make the
formula auditable, but do not make its output an observed pick weight.

## 4. Receipt proxy audit

`backend/app/models/analytics.py` defines `FactReceiptDaily` with
`receipt_date`, factory identity and `weight_kg`. Its grain is:

```text
SEASON x RECEIPT_DATE x FACTORY x FARM_KEY x SUBFARM_KEY x VARIETY
```

The event is factory receipt/arrival, not farm pick. It may be useful for
secondary diagnostics, but it is forbidden as the primary Q2C actual label.
It cannot be made equivalent by matching units or by using the same farm and
variety dimensions.

```text
RECEIPT_PROXY_STATUS=FORBIDDEN_RECEIPT_PROXY
RECEIPT_PROXY_PRIMARY_LABEL=false
```

## 6. Evidence gaps

The following are independent blockers, not implementation tasks hidden in the
audit:

1. No authorized business owner attestation is present for the source boundary
   of `model_harvested_marketable_quantity_kg`.
2. No evidence proves that model marketability and actual picked weight apply
   the same sorting/rejection boundary.
3. No evidence proves the same post-harvest handling boundary.
4. No live external data or real committed source coverage was inspected.
5. The repository has production paths for actual import, commit and I7
   snapshot, but Q2C does not claim rows exist or that an external source has
   been connected.
6. A forecast row's structural grain is compatible, but Q2C does not authorize
   a new membership transformation or aggregate repair.

Accordingly:

```text
BUSINESS_SOURCE_ATTESTATION=NOT_AVAILABLE
MARKETABILITY_EQUIVALENCE=NOT_VERIFIED
SORTING_BOUNDARY_EQUIVALENCE=NOT_VERIFIED
POSTHARVEST_BOUNDARY_EQUIVALENCE=NOT_VERIFIED
TIME_BASIS_EQUIVALENCE=PARTIAL_CONTRACT_COMPATIBLE_NOT_VERIFIED
GRAIN_EQUIVALENCE=PARTIAL_CONTRACT_COMPATIBLE_NOT_VERIFIED
Q2C_V1_FORECAST_TARGET=UNRESOLVED
PHYSICAL_TARGET_ALIGNMENT=BLOCKED_BY_MISSING_BUSINESS_ATTESTATION
Q2B_PHYSICAL_TARGET_BLOCKER=OPEN
```

## 8. Future evidence and hash requirements

A future implementation must store, for every accepted equivalence decision:

- source system/dataset/version;
- attestation version and hash;
- actual event and quantity boundary;
- weighing and date-assignment policies;
- forecast field and forecast authority version;
- sorting/post-harvest transformation identity, if any;
- grain and membership manifest hash;
- decision outcome and policy version.

Hashes must use stable business identities, canonical Decimal values, explicit
units, dates, versions and policy fields. They must exclude database IDs,
insertion order, runtime host, credentials and unbounded raw business rows.

`PROVEN_EXACT` is permitted only when no transformation is required and every
boundary is verified. A versioned transformation may yield
`PROVEN_AFTER_VERSIONED_TRANSFORMATION`; an undocumented rate adjustment may
not.
