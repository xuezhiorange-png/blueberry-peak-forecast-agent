## 1. Release boundary

Point-in-Time forecast validation. It does not establish that the frozen
forecast model has passed real prospective accuracy validation, and it does
not establish that weather has incremental predictive value.

The version is therefore an engineering closeout, not an accuracy approval or

## 4. What each Slice delivered

### S1 — Point-in-Time Data Foundation

S1 established append-only, immutable PIT records and shared visibility rules:

- `forecast_run_snapshot` and daily child rows preserve request, input
  identities, model artifacts, output, warnings, and hashes;
- `area_revision` binds a versioned area value and area semantics to a run;
- `weather_forecast_snapshot` is separate from realized weather and accepts
  only forecast-time/as-issued records;
- `realized_weather_observation` and `phenology_observation` are separate
  immutable facts;
- the existing actual-harvest authority is reused rather than duplicated;
- canonical input hashing binds the complete PIT input identity;
- scope, timestamp ordering, season binding, and future-record visibility fail
  closed.

### S2 — Shadow Forecast and Weather Capture

S2 added the real shadow-forecast path and qualified ECMWF IFS Open Data
capture. It supports deterministic single-base and 39-Base capture, preserves
raw/normalized weather identities, and records weather as PIT evidence only:

```ini
FORECAST_MODE=SHADOW
MODEL_STATUS=EXPERIMENTAL
WEATHER_PROVIDER=ECMWF_IFS_OPEN_DATA
WEATHER_CAPTURED_BASE_COUNT=39
WEATHER_USED_BY_MODEL=false
```

No ERA5-Land realized/reanalysis record is treated as forecast-time weather.
Offline deterministic provider fixtures and the preserved real capture
manifest prove the adapter contract; they do not create matured forecast/actual
business evidence by themselves.

### S3 — Forecast vs Actual Evaluation

S3 established immutable forecast-to-actual and forecast-weather-to-realized-
weather evaluation authorities. It supports full available range and
`AS_OF_DATE` evaluation, future-actual exclusion, revision visibility,
missing-versus-confirmed-zero semantics, season/daily/peak/rolling-7-day
metrics, weather horizons D1/D3/D7/D15, canonical evaluation hashes, and
round-trip persistence.

The S3 fixture and contract acceptance passed. The real authority at the
closeout boundary still reports:

```ini
REAL_EVALUATED_FORECAST_RUN_COUNT=0
REAL_EVALUATED_BASE_COUNT=0
REAL_ACTUAL_COVERAGE_STATUS=INSUFFICIENT_MATURED_ACTUAL_EVIDENCE
GDD_EVALUATION_STATUS=NOT_EVALUATED_DEFINITION_NOT_FROZEN
```

### S4 — Prospective Validation and Weather Value Assessment

S4 established the prospective-eligibility registry, Model A freeze checks,
weather-quality versus weather-value separation, deterministic residual
diagnostics, evidence-sufficiency reporting, and immutable assessment
persistence. It refuses to promote retrospective reconstruction or fixtures to
prospective evidence.

The implementation is complete, but the real evidence gate remains explicit:

```ini
PROSPECTIVE_VALIDATION_STATUS=INSUFFICIENT_MATURED_PIT_EVIDENCE
WEATHER_INCREMENTAL_VALUE=INCONCLUSIVE
V0_7_WEATHER_MODEL_RECOMMENDATION=INSUFFICIENT_EVIDENCE
```

## 5. Historical data versus prospective evidence

Repository evidence confirms that historical harvest data exists across three
seasons:

```ini
HISTORICAL_HARVEST_DATA_AVAILABLE=true
MULTI_SEASON_HISTORICAL_DATA_AVAILABLE=true
THREE_SEASON_HISTORICAL_DATA_AVAILABLE=true
FORMAL_THREE_SEASON_INDEPENDENT_MODEL_ACCEPTANCE_COMPLETE=false
```

The three-season statement is an availability statement, not a claim that all
three seasons are complete, fully identity-covered, PIT-blind, or accepted as
an independent production model test. The evidence records mapped/recorded
subtotals, partial coverage, business-season boundaries, and right-censoring
where applicable. Exploratory backtests remain exploratory.

In particular, historical harvest availability cannot substitute for a
forecast snapshot created before the later actual harvest. Prospective
eligibility requires the immutable forecast timestamp, input/result hashes,
as-issued weather identity, and later actual authority to prove the ordering.
The current count of such eligible matured runs is zero.

## 6. Current capability and non-claims

V0.6 can now represent and replay the intended chain:

```text
PIT-known inputs
  → immutable forecast snapshot
  → later actual harvest / realized weather
  → S3 evaluation
  → prospective eligibility and weather-value assessment
```

The following claims are deliberately not made:

- V0.6 model accuracy has not been validated by real prospective evidence;
- weather has not been shown to improve forecast quality or peak timing;
- a weather-aware model is not complete or promoted;
- V0.5/V0.6 outputs are not granted production accuracy approval merely because
  the engineering and fixture contracts pass.

## 8. Next-phase direction (not implemented here)

```ini
NEXT_PHASE=FORMAL_MULTI_SEASON_MODEL_VALIDATION_AND_WEATHER_AWARE_MODEL_EXPERIMENT
```

The next phase should first use the available multi-season historical data to
run a formal independent-season validation of the frozen area model, then
establish a held-out comparison between Model A and a weather-aware
experimental candidate using only valid forecast-time or otherwise explicitly
authorized inputs. It must report total, daily, single-day peak, rolling
7-day peak, Base stratification, and leakage controls before any model
promotion decision.

The following remain open questions for that phase:

1. What is the formal independent multi-season performance of the current area
   model?
2. What are season-total, daily, single-day peak, and rolling-7-day errors?
3. Which Bases are stable and which are unstable?
4. Can historical or forecast-time weather explain the residuals without
   hindsight leakage?
5. Does a weather-aware experiment outperform Model A under held-out validation?

No V0.7 code, model training, new backtest, scheduler, live operation, or
deployment is part of this Closeout PR.
