## F01：目录冲突后旧预测仍保留（已复现）

来源：`frontend/src/dashboard/components/AuthorizedSavedRunSelector.tsx` 的 load()。
scope/list 的 grant_revision 或 catalog_snapshot 不一致时，代码在客户端构造
409 DIRECTORY_CHANGED，但 catch 只设置 error，不像 select() 的 409 分支那样
调用 invalidateSecurity("access")。

复现：使用实际 ForecastProvider、选择器及请求校验代码，种入明确 SYNTHETIC 的
旧合法上下文；返回两个合法 Schema、但 revision 或 snapshot 不一致的 HTTP DTO。
界面已经显示“来源身份不一致”，上下文仍为 SYNTHETIC_OLD_CONTEXT，而不是 CLEARED。
两个独立测试均失败，StrictMode 下重现。没有 mock 授权函数或修改组件。

这证明本地冲突清理缺陷；**不证明服务器已泄漏未授权数据**。该探针使用合成 fetch
响应，是定位客户端缺陷的单元测试，不是实际 HTTP/PostgreSQL/浏览器全链路验收。

最小修复建议（尚未授权）：仅定向修改该组件冲突处理；增加现有 ForecastContext/
SessionGate 联动回归，确保旧日期、结果和排名一起失效、迟到响应不恢复旧状态。
不应为了修复此点放宽服务器认证或改动历史证据。

## F02：模拟响应未绑定提交产能及情景版本（已复现）

来源：`frontend/src/dashboard/api/client.ts` 的 verifyScenario()。
它核对 forecast/cost/hash、规划级别、情景 ID 和日期，但没有核对返回的每日原始
产能输入与 scenario_version。使用既有 SYNTHETIC 夹具，将请求首日 DIRECT 产能改为
999999 并修改 scenario_version，实际 simulate() 仍接受旧 fixture 的 READY 响应。
“应拒绝该响应”的断言失败。compare() 同样调用该校验函数，尚未新增其单独探针。

这证明客户端响应绑定缺口，**不证明服务端计算错误、真实网络串包或错误业务 Hash**。
未来修复应验证原始输入身份/语义，不在浏览器重算 backlog、损失、排名或预测总量。
最小修复范围候选为该客户端及直接单元/浏览器回归；是否需要额外 Schema 更改需先审查。

## 待进一步确认的后端线索（非 PostgreSQL 运行结论）

辅助源码审查发现两个应交给独立审查和定向复现的线索：

1. authenticate 返回 Principal 后，到 authorize()/DiscoveryService 读取业务前，未再

   需要实际 PostgreSQL barrier 测试区分“已获准在途请求”和“撤权后的新读准入”，

   PREAUTH 且均持有效密码的并发登录可能都成功。需要真实 PostgreSQL 双请求复现。
   目前不宣称密码绕过或真实会话泄露，也不擅自修改该路径。
