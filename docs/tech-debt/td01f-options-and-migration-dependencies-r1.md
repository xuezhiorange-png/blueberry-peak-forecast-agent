## 建议与可执行顺序（全部远端步骤待单独授权）

**建议优先A，工程可行性为PARTIAL，尚非可发布的完整替代仓库。**
它能隔离公开代码与私有历史的生命周期，保留原证据字节及现有验收入口；代价是公开子集
必须完成剩余代码审阅、非代码依赖拆分及CI迁移。B的真实清理可行性仍为BLOCKED_PENDING_OWNER_SCOPE。

1. Owner决定D02/D03/D06，指定私有保管人、访问/审计范围、备份和恢复权限。
2. 只针对已决定的对象建立新允许清单；保留原件及其身份，不用合成数据冒充真实训练源。
3. 在本地继续验证被准入模块的依赖闭包，保留本轮1项失败及3项Commit缺失预检证据；完整新库CI未通过前不得称等价替代。
4. Owner若授权A：先确认原库私有化的协作/公开Fork/入口影响与遏制顺序，验证受控备份，再分别授权可见性变更及新远端创建。不要先建新Public仓库就宣布风险消除。
5. 新公开库只能新根、无Remote/Alternates导入、无历史Tag迁入；配置独立Actions/MCP/发布入口和防再引入检查，再逐模块验收。
6. Owner若改选B：先在受控副本完成精确范围和身份迁移、备份恢复演练；冻结协作写入，再另行批准真实改写、强推、Tag/Release处置及GitHub侧支持协调。本轮不提供可误执行的真实仓库清除脚本。
7. 两种方案均在远端读取元数据验证预期结果，并协调既有克隆/引用；未核验的副本保留风险，不作清除承诺。

**停止条件**：无公开范围决定、无法核对原Hash、需要保留整个未审旧Tree、任何真实源被替换、
完整CI/来源/PIT合同被削弱、备份恢复不成立或授权与实际远端不匹配，立即停止远端实施。
本轮的自动清理仅删除验证器自己创建的临时目录，不涉及用户卷、原数据或原Git对象。
